# Chapter 02 — ledger (written before the prose, 2026-09-02)

Sources: `resources/sources/02/`. Verdict vocabulary: CONTEXT §4. Each folk cell quotes a named retelling that makes the claim; the record cell cites the document and section. The chapter's argument is row 2 against rows 4 and 5: there were three defaults, not one, and the folk story collapses them into a single "insecure until 3.6".

| # | Folk claim (retelling) | Record (document, page/section) | Verdict |
|---|---|---|---|
| 1 | The attacks hit "only those left accessible via the Internet and without a password on the administrator account"; the data was not encrypted but "exported … and replaced" with a ransom note (Bleeping, 3 and 7 Jan 2017, quoting Gevers: "This is not ransomware. Database does not get encrypted. It only gets replaced."). | Nilsson, MongoDB blog, 6 Jan 2017: "In the recent cases we've seen, the attacker has dropped databases and/or collections and replaced them with a new one with a ransom demand." Ottenheimer, MongoDB blog, 8 Sep 2017: "users left systems insecure – connected to the Internet with no password on their Administrator account". Shadowserver's instrument description: a no-auth probe that lists "the first five databases that were returned". | HOLDS — two conditions, reachable and unauthenticated, and a drop-and-replace, not encryption. The vendor's two posts say the same thing the trackers said. |
| 2 | "MongoDB will no longer come with an unsafe configuration out of the box" as of 3.6 (TNW, 8 Nov 2017); "Because of MongoDB's default security configuration, which allows any user full access to the database" (Wikipedia § Security); "up until recently, the software's default configuration is insecure" (Register, 9 Jan 2017). | SERVER-4216, "mongodb 10gen debian package listens on all interfaces by default", filed 4 Nov 2011, closed 8 Apr 2014, fix version 2.6.0-rc0. 2.6 release notes dated April 8, 2014. 3.6 release notes § "Default Bind to Localhost": "From MongoDB versions 2.6 to 3.4, only the binaries from the official MongoDB RPM … and DEB … packages would bind to localhost by default." Ottenheimer, 8 Sep 2017: "since release 2.6.0 we have made localhost binding the default configuration in our most popular deployment package formats, RPM and deb." | WRONG — for the package most people installed from, the safe bind default was nearly three years old when the wave hit. What 3.6 changed was *where* the default lived: the binary instead of a package's config file. There were three defaults, not one. |
| 3 | "If installed on a server with the default settings, for example, MongoDB allows anyone to browse the databases, download them, or even write over them and delete them." (Krebs, 10 Jan 2017; the post carries a 1:55 p.m. correction, "Clarified the default settings of a MongoDB installation".) | Commit 60636b4, `listen.cpp`, before the change: an empty `bind_ip` meant `SockAddr("0.0.0.0", port)` — the binary's default. SERVER-4216: the Debian package's `mongodb.conf` lacked `bind_ip 127.0.0.1` until 2.6.0. Matherly, Shodan, Jul 2015: "2.4.14 seems to be the last version that still listened to 0.0.0.0 by default"; 40% of exposed instances ran 1.8.1. Horowitz to TNW, Nov 2017: "If you explicitly turn it on, but don't turn on authentication, we can't help you at that point." | OVERSTATED — true of the tarball, the pre-2.6 packages and the cloud images built from them; not true of an RPM/DEB install after April 2014. And the other half of "default settings", no authentication, was never changed, in 3.6 or since: the bind default moved, the auth default did not. |
| 4 | "About 78% of all these hosts were running known vulnerable versions" and MongoDB "has fixed this issue a few months later, but companies keep using the outdated versions … because those versions were the default MongoDB images on AWS" (Gevers via Bleeping, 3 Jan 2017). | Matherly, Shodan, 15 Dec 2015: the most common exposed versions were 3.0.7 (3,010), 2.4.9, 2.4.14, 2.4.10 and 3.0.6; "By default, newer versions of MongoDB only listen on localhost. The fact that MongoDB 3.0 is well-represented means that a lot of people are changing the default configuration of MongoDB to something less secure … It could be that users are upgrading their instances but using their existing, insecure configuration files." SERVER-28229's own "User Summary" shows the override: `bindIp: 0.0.0.0`. | MISSING — old versions and cloud images are in the folk story; the third population is not: hosts on versions whose packages already defaulted to localhost, reconfigured by hand to listen everywhere. A default only protects the installs that keep it, and Shodan had said so thirteen months before the wave. |
| 5 | "MongoDB 3.6 comes hardened against database ransomware by default" (TNW headline, 8 Nov 2017); "With MongoDB 3.6, this default behavior is implemented directly in the server itself" (MongoDB press release, 8 Nov 2017). The change is dated to the 3.6 announcement, ten months after the wave. | SERVER-28229, "Bind to localhost by default", created 7 Mar 2017 (nine weeks after Nilsson's post), original description: "All mongod and mongos 3.6 binaries shall bind to 127.0.0.1 by default"; a startup warning; a `--bind_ip_all` flag. Commit 60636b4 authored 25 Apr, committed 28 Apr 2017, fix version 3.5.7. JIRA "User Summary as of May 17, 2017": "as of this release, MongoDB servers will only listen for connections on the local host". docker-library/mongo #180: "3.5.7 now binds to localhost-only by default". Ottenheimer, 8 Sep 2017: "Beginning with development release version 3.5.7, localhost-only binding is implemented directly in the MongoDB server". 3.6 GA 8 Nov 2017. | MISSING — the change was specified in March and merged in April, seven months before GA; it sat in a development release while the September wave took 26,000 more. The gap between merge and reach is the defense story, and the folk story's date hides it. |
| 6 | "Body count hits 27,000 in hours" (Register, 9 Jan 2017); "at least 29,000 MongoDB databases that were previously published online are now erased" (Krebs, 10 Jan, quoting Merrigan); "more than a quarter of the 99,000 MongoDB instances open to the internet have been compromised" (ZDNet, 9 Jan). | The count's method, from Krebs: Gevers ran the Shodan query and saw databases "with names like 'readme,' 'readnow,' 'encrypted' and 'readplease'"; Merrigan: re-run the query minutes later and "many now have a different database title and a new ransom note". Bleeping, 7 Jan: "attackers are deleting each others' ransoms as quick as they pop up"; Gevers in 84 cases found no "trace of data exfiltration". The Gevers/Merrigan sheet, first tab: per actor, "Name of replaced DB" and "Victims (OSINT)"; totals row 86,993 OSINT victims against 102 helped, undated, cumulative to 2019. Denominators in the same week: 99,000 (Gevers), "more than 52,000" (Shodan via Krebs, 10 Jan), ~42,000 implied by Bleeping's "10,500 … about 25%". | OVERSTATED — the number is a count of ransom-note database names seen by a scanner, under whichever note was last written, against a denominator that varied by a factor of two. "Erased" holds; "held for ransom" mostly meant deleted, since the trackers found no export in most cases they checked. |
| 7 | MongoDB "blamed the attacks – and rightfully so – on database owners who failed to set a password for their databases, and then left their servers exposed online without a firewall" (ZDNet, 1 Jul 2020, on Ottenheimer). | Nilsson, 6 Jan 2017: "These attacks are preventable with the extensive security protections built into MongoDB. You need to use these features correctly"; "The most popular installer for MongoDB (RPM) limits network access to localhost by default. Use this configuration too if you're installing via another means." Then SERVER-28229, 7 Mar 2017: "MongoDB binaries should bind to localhost by default … while not being accessible from the internet." Then the press release, 8 Nov 2017: "all MongoDB packages across all platforms refuse all external connections to the database unless otherwise explicitly configured by the administrator." | OVERSTATED — the statement is quoted accurately and the story stops there. Nine weeks after telling users to set the bind address themselves, the vendor filed a ticket to set it for them, and shipped it. The change is the vendor's real post-mortem; the January post is not. |
| 8 | "If you don't explicitly turn it on, that entire method of doing ransomware goes away" (Horowitz to TNW, 8 Nov 2017). | Bleeping, 4 Sep 2017: 26,000 new victims in one week, 22,449 to one group, four months after 3.5.7; "over 45,000" cumulative. Gevers: "Are they running on older version without safe defaults …?" ZDNet, 1 Jul 2020: 22,900 databases ransomed in one 2020 campaign, "roughly 47% of all MongoDB databases accessible online"; "another 3,000 in February 2019". Matherly, May 2020: the attacks "are still on-going". | OVERSTATED — true for a fresh 3.6 install that keeps its default; the method did not go away for the installed base, the images, or anyone who set `bindIp: 0.0.0.0` from the fix ticket's own instructions. |
| 9 | "The default changed to localhost and the exposed count fell" (this book's own CONTEXT §3 before 2 Sep 2026); "From the 60,000 MongoDB servers left exposed online in early 2017, the needle has barely moved to 48,000" (ZDNet, 1 Jul 2020). | Shodan's series: "nearly 30,000 instances", 595.2 TB (18 Jul 2015); "at least 35,000", 684.8 TB (15 Dec 2015); "more than 52,000" (10 Jan 2017, via Krebs); exposed MongoDB *data* "from 24 TB to 12.5 TB" 2018→2020, "the only database among the 3 … where the amount of exposed data has actually decreased" (10 May 2020) — with the 2018 figure "already drastically lower … due to a series of ransomware attacks". ZDNet's 60,000→48,000 states no source; its "22,900 … roughly 47%" implies ~48,700. Shadowserver's daily open-MongoDB feed would settle it and was not obtained. | OPEN — exposed data fell, and Shodan's own reading is that the wipes did much of that. Whether the number of exposed hosts fell is not on the record: the one series that says so is unsourced. A dated Shodan or Shadowserver host count from 2017 and 2020, same method, would close this row. |
