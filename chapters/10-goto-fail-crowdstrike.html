Chapter 10 · A10:2025 Mishandling of Exceptional Conditions

One Line Too Many, One Field Too Few

You know both headlines. In February 2014 a duplicated goto fail; in Apple's TLS code let anyone on the network pose as any server. In July 2024 a CrowdStrike update turned an estimated 8.5 million Windows machines into blue screens. The record adds the detail the headlines skip: the two bugs failed in opposite directions. Apple's never raised an error. It returned success from a label called fail. CrowdStrike's raised an error that nothing could catch; the crash text, in Windows' own words, reads "This cannot be protected by try-except". Each was fixed by a small change. Neither change is the lesson.

The break

On 21 February 2014 Apple shipped iOS 7.0.6, iOS 6.1.6 and, four days later in the same batch of notes, OS X 10.9.2. The security note for all three carried the same two sentences and nothing else. Impact: "An attacker with a privileged network position may capture or modify data in sessions protected by SSL/TLS". Description: "Secure Transport failed to validate the authenticity of the connection. This issue was addressed by restoring missing validation steps". That is the whole of what Apple has ever said about CVE-2014-1266.

The next day Adam Langley, who worked on TLS for Google's Chrome, wrote the post everyone else has been quoting since. He noted the cat was already out of the bag on Hacker News, then quoted the bug "from Apple's published source code" and explained why "the signature verification will never fail". The file is public. In the release Apple tagged Security-55471, libsecurity_ssl/lib/sslKeyExchange.c, lines 623 to 633 read like this. 

    if ((err = ReadyHash(&SSLHashSHA1, &hashCtx)) != 0)
        goto fail;
    if ((err = SSLHashSHA1.update(&hashCtx, &clientRandom)) != 0)
        goto fail;
    if ((err = SSLHashSHA1.update(&hashCtx, &serverRandom)) != 0)
        goto fail;
    if ((err = SSLHashSHA1.update(&hashCtx, &signedParams)) != 0)
        goto fail;
        goto fail;
    if ((err = SSLHashSHA1.final(&hashCtx, &hashOut)) != 0)
        goto fail;

    err = sslRawVerify(ctx, ctx->peerPubKey, dataToSign, dataToSignLen,
                       signature, signatureLen);
    ...
fail:
    SSLFreeBuffer(&signedHashes);
    SSLFreeBuffer(&hashCtx);
    return err;

The label at the bottom frees two buffers and returns err. The second goto fail; is indented as if it belonged to the if above it. It does not; C binds only the first statement to an unbraced if. So the jump always happens, err still holds the zero that the successful hash update left in it, and the function returns "no error" without ever reaching sslRawVerify. That call is the one that checks the signature.

What signature? The function's name says it: the server's signature on the ServerKeyExchange message, which DHE and ECDHE cipher suites use to hand over the ephemeral key for the connection. Langley put the consequence in one line: "It's possible to send a correct certificate chain to the client, but sign the handshake with the wrong private key, or not sign it at all". The CVE record says the same thing more formally. The code "does not check the signature in a TLS Server Key Exchange message", so an attacker can "spoof SSL servers by (1) using an arbitrary private key for the signing step or (2) omitting the signing step".

The reach was everything built on SecureTransport, which on those platforms was most software. Chrome and Firefox were the exceptions, because they carried their own TLS stack, NSS. TLS 1.2 used a different verification function, and plain RSA suites send no ServerKeyExchange at all; neither fact helped, because the attacker in the middle picks the version and the suite. Certificate pinning would not have helped either. The chain was genuine; the broken link was between the chain and the handshake. The bug was in iOS 6 as well as 7, which is why iOS 6.1.6 shipped the same day.

The fix is also public. Between Security-55471 and Security-55471.14, the release for OS X 10.9.2, the entire change to this file is one deleted line: line 631, goto fail;. How the line got there, Apple has never said. David Wheeler, whose essay on the bug is the most-cited attempt at lessons, writes plainly: "I have not found any data on why the line was duplicated". The folk story, then, is the one Ars Technica printed on day one, "a single line of misplaced code", and Wikipedia's "two successive goto fail statements", the second "unconditional". Wheeler's version of the effect is the one that travels: "invalid certificates were quietly accepted as valid". The ledger tests that sentence.

Ten years later the other failure. On Friday 19 July 2024 at 04:09 UTC CrowdStrike released a content update for its Windows sensor; it was reverted at 05:27. Windows hosts running sensor 7.11 or later that were online in those 78 minutes and received it crashed. Mac and Linux were not affected. By that evening the company's chief executive had said the sentence every incident now needs: "This was not a cyberattack". The next day Microsoft, whose name was in most of the headlines, published its estimate, "8.5 million Windows devices, or less than one percent of all Windows machines", and its own disclaimer, "this was not a Microsoft incident".

CrowdStrike's Preliminary Post Incident Review of 24 July explained a vocabulary the public had never needed. The sensor takes two kinds of content. Sensor Content ships with the sensor itself and includes Template Types, "expressed in code". Rapid Response Content is configuration pushed from the cloud, "not code or a kernel driver", delivered as Template Instances of a Template Type, through numbered Channel Files. Sensor 7.11, released 28 February 2024, added a Template Type for inter-process communication. It was stress-tested on 5 March, a first instance went out the same day via Channel File 291, and three more followed in April. All "performed as expected".

On 19 July two more instances were deployed. "Due to a bug in the Content Validator, one of the two Template Instances passed validation despite containing problematic content data". On the sensor the result was "an out-of-bounds memory read triggering an exception. This unexpected exception could not be gracefully handled, resulting in a Windows operating system crash (BSOD)".

The Root Cause Analysis of 6 August said what "problematic" meant. "The new IPC Template Type defined 21 input parameter fields, but the integration code that invoked the Content Interpreter with Channel File 291's Template Instances supplied only 20 input values". That mismatch had been live since February. Nobody had noticed because every test and every earlier instance used a wildcard in the 21st field, so the sensor never had to look at it. One of the 19 July instances "introduced a non-wildcard matching criterion for the 21st input parameter". "At the next IPC notification from the operating system" the interpreter went looking for a 21st value in a 20-value array. The RCA calls it "the confluence of these issues": the validator believed the definition, the interpreter believed the code, and no test had ever asked for field 21.

By 29 July about 99% of Windows sensors were back online, by CrowdStrike's count. On 25 October Delta Air Lines sued in Fulton County, Georgia, alleging over $500 million in out-of-pocket losses and roughly 7,000 cancelled flights over five days. That is a complaint. In May 2025 the court let the negligence and computer-trespass counts proceed and cut the fraud counts, according to press reports of the order. No court has found a number. The folk story here is Wikipedia's lede: a "faulty update", "roughly 8.5 million systems", "the largest outage in the history of information technology", and a fix "within hours".

The mechanism

OWASP's 2025 list has a category for this, and it is new: Mishandling of Exceptional Conditions is a new category for 2025. Its definition: Mishandling exceptional conditions in software happens when programs fail to prevent, detect, and respond to unusual and unpredictable situations, which leads to crashes, unexpected behavior, and sometimes vulnerabilities. Among the weaknesses it maps is CWE-636 Not Failing Securely ('Failing Open'). Read the two incidents against that sentence and the pattern is not "a bad line" or "a bad update". It is that in both cases a check ran, and it was not the check that mattered.

Draw the Apple function as three boxes. Box one: a chain of steps, each written as if ((err = step()) != 0) goto fail;. Box two: the verify call, the only step that can say a signature is bad. Box three: the label, which frees memory and returns err. The idiom is fine as long as two things hold: the label is reached only by a failed step, and the last step before it wrote err. The duplicate line broke the first. Control now reaches the label from a step that succeeded, and err faithfully reports that success.

The label lies, and it lied before the bug. Look at the end of the function: after sslRawVerify there is no separate success exit. Success also falls through to fail:. The label was never "failure"; it was "cleanup and return whatever err is". In that design a stray jump is not a crash or a rejection. It is an early return with the current status, and the current status was zero. That is what failing open looks like in C: an absence of error standing in for a positive result.

Why did nobody see it? Langley wrote a six-line version of the bug and compiled it with all warnings on: "neither GCC 4.8.2 or Clang 3.3 from Xcode make a peep about the dead code". Clang could warn, with -Wunreachable-code, but that flag was not part of -Wall. Wheeler later checked gcc and found something worse: it accepted the same flag and did nothing, without saying so. Indentation shows what the writer meant. The compiler reads braces. When they disagree, the eye sides with the indentation, and the eye reviews the code.

Now draw the CrowdStrike sensor, also in three boxes. Box one: a definitions file that says this Template Type has 21 fields. Box two: the sensor code, which builds an array of 20 pointers from a named-pipe event and hands it to the interpreter. Box three: a rule, sent from the cloud, that says "compare field 21 against this pattern". The interpreter asks for index 20 of a 20-element array and gets whatever lies past the end; in the published crash dump it is a value that "does not point to valid memory". The code then checks that pointer for NULL, which it is not, and reads through it. A check ran. It was the wrong check: the right question was "is 20 in range", not "is this null".

Because the code runs in csagent.sys, a file-system filter driver loaded early in boot, the bad read is not an exception a program can catch. It is a bugcheck. The RCA reproduces the debugger's summary: "PAGE_FAULT_IN_NONPAGED_AREA (50) Invalid system memory was referenced. This cannot be protected by try-except". The machine stops, and because the driver loads at boot, it stops again on restart. That is failing closed, done by the operating system on the sensor's behalf.

OWASP's page has a line that fits both drawings: Any time an application is unsure of its next instruction, an exceptional condition has been mishandled. Apple's code was unsure whether it had verified anything and answered yes. CrowdStrike's was unsure whether field 21 existed and answered by reading it. Neither is a web application; the book's spine is the OWASP list, and this chapter is the one furthest from it. An out-of-bounds read is memory safety, CWE-125, which is not on A10's list at all. What puts both cases here is the handling, not the fault.

The defense

OWASP's advice is to 'catch' every possible system error directly at the place where they occur and then handle it, and, mid-transaction, roll back every part of the transaction and start again (also known as failing closed). The two incidents test that advice from both ends. One shows what happens when you do not fail closed. The other shows what happens when you do, at the wrong size.

Apple's code failed open at the one boundary where failing closed is not optional: authentication. The fail-closed form of the same idiom is small. Start err as a failure, so a stray jump returns "bad". Or give the verify call the only path to "ok", so no earlier step's success can be mistaken for it. Apple did neither in the fix; the diff deletes the line and leaves the structure. Whether the structure changed later, or whether a test or a review rule was added, Apple has not said, and no document shows it. The defense record on the Apple side is two sentences and a one-line diff.

What outsiders said would have caught it is opinion, and the opinions disagree. Langley: "A test case could have caught this, but it's difficult because it's so deep into the handshake. One needs to write a completely separate TLS stack"; code review "can be effective". Wheeler: negative tests and clang's flag. Both are plausible. Neither is a record of a defense that worked. The only defense in the record that demonstrably did work is diversity. Chrome and Firefox were fine because they did not use Apple's stack. Langley's port-1266 server, sending real certificates and a wrong signature, is the other: a negative test, built after the fact, that any client could run.

CrowdStrike's sensor failed closed, and Windows made sure of it. Microsoft's explanation, a week after the outage, is the clearest statement of the rule: "All code operating at kernel level requires extensive validation because it cannot fail and restart like a normal user application". And the price: "Kernel drivers provide the above properties at the cost of resilience". For a security sensor, failing closed is the defensible default. The fail-open version is a sensor that silently stops watching, and the CEO's first statement shows how much that version is feared: "There is no impact to any protection if the Falcon sensor is installed".

But what failed on 19 July was one telemetry rule in one channel file. The host did not need to close for that rule to be safe; the rule needed to be skipped. That is exactly what CrowdStrike's own fix does. The bounds check added on 25 July "prevents the Content Interpreter from performing an out-of-bounds access of the input array and crashing the system"; it reached all Windows sensors 7.11 and later by 9 August. A compile-time check that the field count matches went to production on 27 July, and the validator was changed to allow only a wildcard in field 21. Read carefully, the code fix is a fail-open at a smaller boundary: the rule fails, the machine runs. Fail closed at the machine was the wrong size.

The other half of the fix is about what a customer could pin. Before the incident customers chose the sensor version, N, N-1 or N-2, and the review says so with some pride: "Customers have complete control over the deployment of the sensor". Content was not the sensor. It arrived from the cloud, to every host, at once. Finding 6 of the RCA adds canary rings and, for the first time, lets customers "choose where and when Rapid Response Content updates are deployed". The twelve automated tests that passed the Template Type all used a wildcard in the field that mattered; Finding 5 concedes that the instance was validated but never run in the interpreter, and adds that step.

Did it work? The RCA says the scenario "is now incapable of recurring", which is the vendor's claim about its own fix. Two independent reviews were commissioned; no published findings were found for this chapter. So the outcome side of the defense record is thin, and a reader should hold it that way until a review is published or another year passes without a Channel File 292. What the record does settle is the shape of the decision. "Fail closed" and "fail open" are not properties of a system. They are properties of a boundary, and the boundary is chosen. Apple's was chosen by accident, open, where closed was right. CrowdStrike's was chosen by the platform, closed, around a whole machine, when the failing unit was a rule.

What you can now see

Find one place in a system you run where an error path and a success path share an exit. In C it is a cleanup label; elsewhere it is a finally, a deferred close, a catch block that returns a status variable. Ask one question of it: if control arrives here without any check having run, what does it return? If the answer is "whatever the variable held", and the variable starts at success, you have Apple's bug without the duplicate line. It is waiting for one.

Then find the mirror. Somewhere a component of yours is driven by configuration it did not write: a rules file, a feature flag, a template, a schema someone else owns. Ask what happens the first time that configuration names a field the code has never supplied. If the answer is "it can't", check who counts the fields and where; CrowdStrike's definition said 21 and its code said 20 for five months. If the answer is "it crashes", decide now how much should crash. The rule, the process, or the machine. That is the decision A10 is about, and it is only a decision if you make it before the field arrives.
