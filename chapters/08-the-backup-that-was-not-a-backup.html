Chapter 8 · A08:2025 Software or Data Integrity Failures

The backup that was not a backup

The familiar Maersk story ends with one domain controller spared by a power cut in Ghana. The firmer first-person record begins one step later. Gavin Ashton, then working on identity and access management at Maersk, says the first restored controller ran on a Surface Pro 4 after controllers had been lost worldwide. Wired reports that the controllers synchronized their data. That made each a current peer, not a time-separated recovery copy. The unlikely hardware matters because recovery had to begin somewhere outside the live fleet.

The break

On 27 June 2017, NotPetya hit A.P. Moller–Maersk and other companies. Maersk's first investor account said the malware entered through software used to file taxes in Ukraine. Applications and data became unavailable, with the main impact falling on its container businesses. Several systems were shut down as a precaution.

The folk version reduces the entrance to an update server. BleepingComputer wrote that M.E.Doc's update servers “were responsible for the initial NotPetya infections.” On that narrow point, later technical records agree. Cisco Talos concluded after its incident response that every installation it traced came through M.E.Doc's update system. Microsoft reported telemetry in which the legitimate updater process executed a malicious command on 27 June.

Yet “the update server did it” compresses a staged mechanism into one bad download. Cisco says M.E.Doc gave its responders access to engineers and administrators, who walked them through the system, plus logs and code. Their report found that an unknown actor had stolen an administrator's credentials, obtained root privileges and changed the NGINX server configuration. Traffic for M.E.Doc's update host was proxied onward to another server.

Cisco also confirmed earlier research into a backdoor inserted in M.E.Doc software. It identified modified code in update versions dated April, May and June. The code could gather data and download and execute arbitrary code. Its command-line arguments matched Cisco's endpoint telemetry when M.E.Doc machines executed the initial NotPetya sample.

A later US indictment supplies a more exact sequence, but it records allegations, not findings. It alleges that the accused gained access to M.E.Doc's code and modified update files on three dates before the main attack. Customer computers downloaded those files, while NotPetya itself was held back until 27 June.

The indictment alleges that the June update file installed command capability. For several hours on 27 June, traffic bound for the update server was temporarily rerouted to a server controlled by the accused in France. Computers with the altered update could then receive and execute commands, including the command that delivered NotPetya. The compromised update was therefore both a trusted foothold and a later delivery path.

Once inside a network, NotPetya did not depend on every machine contacting M.E.Doc. Microsoft described several lateral-movement methods: stealing credentials or reusing active sessions, copying through file shares, and using legitimate execution features or SMB vulnerabilities. Ashton writes, in a participant's personal account rather than a company post-mortem, that it moved through Maersk into servers and domain controllers.

The label “ransomware” also hides something useful. The BBC called the event the “NotPetya ransomware attack.” The indictment alleges that the ransom was a ruse and that the accused could not decrypt victims' files even after payment. ESET independently examined the disk code and found that its changes made recovery impossible. The payment screen imitated ransomware; the recovery bargain did not exist.

Maersk's immediate problem was operational, not lexical. Its Q2 presentation says teams used many manual workarounds to serve customers and retained full control of vessels. It also said there had been no third-party data breach or data loss. Systems were not one thing: customer service, vessel control, applications, data and identity each had different continuity needs.

Identity became a prerequisite for rebuilding the rest. Ashton says Maersk's disaster-recovery planning had covered the loss of a site or datacentre. It had not covered losing every domain controller everywhere at once. Restoring Active Directory required work across Maersk, Microsoft and partners. Only then did that first controller come up on the Surface.

Wired's oral-history retelling supplies the famous missing scene. It says a controller in Ghana had been knocked offline by a blackout and therefore escaped NotPetya. It calls Maersk's synchronizing controllers a “decentralized backup strategy.” Those details came from Wired's interviews. The fetched Maersk publications do not confirm Ghana or the blackout, and Ashton's account does not name either.

The distinction matters even if Wired's scene is exact. Wired says the controllers synchronized data, so in theory each could replace the others. It immediately adds that this arrangement had not accounted for every controller being wiped simultaneously. A live controller carries current directory state; it is not a time-separated recovery copy.

The account of the destruction is separate. Ashton attributes movement into servers and controllers to pass-the-hash and weakly controlled privileged access. Microsoft's incident analysis lists credential or session reuse, file shares, legitimate execution features and SMB vulnerabilities as lateral paths. Neither says Active Directory replication spread NotPetya at Maersk.

Recovery did not happen at one magic moment. Maersk's A View from the Other Side of a Crisis says almost all its systems became inoperable and needed rebuilding. It says the network was rebuilt in ten days while customers' cargo kept moving. Maersk's annual report put the loss at approximately USD 250–300 million, covering lost revenue, IT restoration and extraordinary operating costs.

Darknet Diaries gives the folk figures as a functioning network after “about nine days” and a cost of USD 350 million. Its approximate timing is compatible with Maersk's “just 10 days,” although the two accounts use different terms for the milestone. The cost is less ambiguous: Maersk's own annual account reports a lower range.

The mechanism

OWASP defines the category this way: Software and data integrity failures relate to code and infrastructure that does not protect against invalid or untrusted code or data being treated as trusted and valid. The important verb is “treated.” An updater is supposed to cross a boundary safely. It takes bytes from elsewhere and gives them the authority of locally installed software.

Draw these four boxes clearly on a whiteboard: source code, build artifact, update service, client. Draw arrows from code to artifact, artifact to service, and service to client. At each arrow, ask two different questions. Did these bytes arrive unchanged? Were these the bytes the authorized publisher meant to release? A protected connection can answer the first question while data travels. It does not by itself answer the second.

A digital signature binds an artifact to a signing key. The publisher calculates a digest of the release and signs that digest with a private key. The updater has the corresponding public key. It calculates the digest again, verifies the signature, and installs only after both checks succeed. A changed byte produces a different digest. A fake publisher lacks the private key needed to make the altered artifact verify.

That is the clean model, but it has a boundary of its own. If an attacker can change code before an authorized build is signed, the signature faithfully authenticates malicious code. The same is true if the signing key or signing service is compromised. Signatures are still valuable. They force an attacker toward a smaller, more controlled part of the release system, and they let a client reject artifacts changed after approval.

The M.E.Doc record shows why all four boxes matter. Cisco found stolen administrator credentials, changed web-server configuration and modified application code. The indictment alleges earlier altered update files followed by temporary rerouting on 27 June. A design that checks only which hostname answered has confused the update service with the release artifact. A design that signs whatever the build emits has moved the question upstream, not answered it.

BleepingComputer reported that M.E.Doc used neither HTTPS nor cryptographically signed binaries. The fetched primary and incident-response documents do not establish that signing state. Cisco's account does establish several compromised control points, but it never says whether the client verified signatures. That claim therefore remains open. A binary, updater specification or forensic report from the period would settle it.

This is also where two OWASP categories can appear to overlap. Cisco called the incident a supply-chain attack because a trusted software vendor delivered a compromised asset to its customers. In the 2025 list, A03 covers failures in managing software dependencies and the broader supply chain. A08 looks lower, at the missing integrity decision where a client accepts code or data as valid.

For this chapter, A08 is a lens rather than a perfect jurisdiction. M.E.Doc was accounting software and Maersk's damaged estate was an enterprise network, not a tested web application. The whiteboard still transfers. Every plugin loader, package installer, CI deployment agent and auto-updater makes the same promotion: remote bytes become trusted instructions. The review question is not merely “Where did we download it?” It is “What evidence must be true before we execute it?”

The defense

OWASP's first prevention is direct: Use digital signatures or similar mechanisms to verify the software or data is from the expected source and has not been altered. The client must enforce that rule before execution. Logging a bad signature and continuing is not an integrity boundary. Neither is hiding an unsigned download behind a familiar product name.

For NotPetya, however, the defense record is thin. None of the fetched primary records says whether the affected M.E.Doc updater required signatures. None shows M.E.Doc adopting a new signing system afterward or measures what it stopped. It would therefore be false to say that signature verification certainly would have blocked this exact chain. The record does not locate the signing key, approval step or build boundary because it does not establish that they existed.

That uncertainty does not make the control ceremonial. It makes the design question more exact. Keep signing authority separate from the update host. Record which reviewed source produced each artifact. Restrict who and what can request a signature. Let clients trust a deliberately distributed verification key, not whatever key arrives beside the update. These controls defend the arrows before and after signing, not only the final download.

OWASP also tells teams to review code and configuration changes, and to segregate and control access to the delivery pipeline. Those controls meet Cisco's findings more completely than signatures alone. Cisco reported both modified code and server configuration after an administrator's credentials were stolen. The defense is a chain of independently enforced decisions because the attack record is a chain of compromised decisions.

Prevention and recovery solve different moments. Once destructive code runs with enough reach, another live copy is not necessarily a way back. A replica answers, “Can another machine serve the latest state?” A backup answers, “Can we recover a known earlier state after the latest state becomes dangerous?” That time boundary is as important as the network boundary.

The UK National Cyber Security Centre says recent offline backups are essential because some malware merely presents itself as ransomware. Its guidance says copies should be separate, ideally offsite, and not permanently connected to the network. It also recommends multiple locations and exercises that assume both onsite systems and cloud backup servers are unusable. This is a documented defense prescription, not a claim about what Maersk had.

Microsoft's Active Directory forest-recovery guide makes the object concrete. Recovery starts by restoring at least one domain controller in each domain from an available backup. A more recent backup contains more useful state, but can also reintroduce dangerous state. Microsoft therefore prefers bringing the first restored controller up while other writable controllers are shut down, preventing unsafe data from replicating back.

The survivor in Wired's Ghana account behaved like an isolated copy at the critical moment. That does not turn it into a designed backup. The record does not show a chosen restore point, a tested recovery image, a retention policy or planned isolation. Ashton instead says the plans covered losing one site or datacentre, not every controller. Accident supplied distance; recovery work still had to turn the surviving state into a directory service.

Maersk's published aftermath is broader and less specific. Its annual report says immediate and long-term initiatives were implemented or planned across cyber resilience, infrastructure, IT continuity, recovery and business continuity. It does not name an offline-backup architecture or report a restoration test. That is enough to document investment, not enough to award a defensive success.

The strongest measured defense in Maersk's record was organizational continuity during recovery. Its early report says manual workarounds served customers and vessel control continued. Its later account says cargo kept moving while the network was rebuilt in ten days. Those claims do not make the interruption small; the annual report's USD 250–300 million range prevents that reading. They show that business continuity can preserve selected outcomes while technical recovery remains unfinished.

What you can now see

Choose one updater or deployment agent in a system you run and draw its promotion path. Start where a change is approved. End where a client executes it. Put the build, artifact store, signing authority and delivery service between them. Then mark the first point at which an attacker controlling one box could make unreviewed bytes look approved.

Do the same drawing once more for recovery, but add time. Find the copy that remains usable if destructive code can reach every current peer through the same administrative paths. If the answer is another live replica, you have availability. You have not yet drawn recovery. The lesson from Maersk is not to hope for a disconnected controller. It is to decide which state must survive outside the production trust boundary, then prove you can restore it.
