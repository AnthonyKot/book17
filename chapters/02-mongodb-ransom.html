Chapter 2 · A02:2025 Security Misconfiguration

Three Defaults, Not One

On 27 December 2016 a Dutch researcher opened one more MongoDB server that had no password and found, where its data had been, a single table named WARNING with a ransom note in it. Within two weeks the trackers' count of such databases passed 27,000. The headline version has held since: MongoDB shipped open to the internet by default, and the ransom wave forced the fix in version 3.6. The vendor's own bug tracker says otherwise. The ticket that made the official packages listen only on localhost was closed in April 2014, nearly three years before the first ransom note. What 3.6 changed was where the default lived.

The break

The folk story has four tellers. Brian Krebs, 10 January 2017: "If installed on a server with the default settings, for example, MongoDB allows anyone to browse the databases, download them, or even write over them and delete them". The Register, the day before: "up until recently, the software's default configuration is insecure". Wikipedia's Security section: "Because of MongoDB's default security configuration, which allows any user full access to the database, data from tens of thousands of MongoDB installations has been stolen". And The Next Web, on the day 3.6 shipped: MongoDB "will no longer come with an unsafe configuration out of the box". One default, insecure, fixed by the wave. Each sentence is nearly true.

The first sighting is Bleeping Computer's, from Victor Gevers. Gevers had spent years finding open servers and reporting them to their owners. On 27 December he found a MongoDB server "left open to external connections and without a password on the admin account" and, instead of its collections, one table named WARNING. Its content, minus the addresses, was "SEND 0.2 BTC TO THIS ADDRESS … AND CONTACT THIS EMAIL WITH YOUR IP OF YOUR SERVER TO RECOVER YOUR DATABASE !". The server's own logs "show clearly that the date [at which] it was exported first and then the new database with tablename WARNING was created". Gevers was precise about the class: "This is not ransomware. Database does not get encrypted. It only gets replaced." That owner had a backup from just before and restored it.

The count began the next week. Bleeping's update of 4 January carried Shodan founder John Matherly's figure: "just over 1,800" databases that appeared to have been hit, and, from the blockchain, at least eleven owners who had paid. Gevers put the exposed population on the cloud, Amazon first, and said "About 78% of all these hosts were running known vulnerable versions". Bleeping's gloss on that sentence is the folk story in one line. The vendor "has fixed this issue a few months later, but companies keep using the outdated versions … because those versions were the default MongoDB images on AWS and other cloud hosting services". Hold that sentence. The vendor's tracker dates the fix differently, and to more than one place.

On 6 January the vendor spoke. Andreas Nilsson, MongoDB's director of product security: "These attacks are preventable with the extensive security protections built into MongoDB. You need to use these features correctly". The post's operative line: "The most popular installer for MongoDB (RPM) limits network access to localhost by default. Use this configuration too if you're installing via another means." Its account of the attack matched Gevers's: "the attacker has dropped databases and/or collections and replaced them with a new one with a ransom demand". Victims were told to "assume that the attacker has a copy of all data".

By 7 January it was a market. Bleeping: the first hacker had been at it since 20 December; "Two days ago there were only three groups, now there are eight". Niall Merrigan, tracking with Gevers, had tweeted 10,500 servers on 6 January, which Bleeping called "about 25% of all MongoDB databases accessible via the Internet". Groups were "re-hacking the same servers and rewriting each other ransom notes", so victims who paid sometimes paid the wrong group. In 84 cases Gevers could find no "trace of data exfiltration". Merrigan: "Right now it's bedlem … attackers are deleting each others' ransoms as quick as they pop up."

Then the weekend. ZDNet on 9 January: some 27,000 servers compromised, "up from an estimated 2,000 on January 3 and 8,542 on January 5", which it put at "more than a quarter of the 99,000 MongoDB instances open to the internet". The Register the same morning, from Merrigan: "from 12,000 earlier today to 27,633, over the course of about 12 hours". It counted fifteen distinct attackers, one of them, kraken0, on 15,482 instances at one bitcoin each with no one appearing to have paid. Gevers put the exposed installations at 99,000. Krebs on 10 January: Merrigan's "at least 29,000 … now erased"; Flashpoint's confirmation of "at least 20,000"; and Shodan's count that day of "more than 52,000 publicly accessible MongoDB databases", the largest share in the United States.

What those numbers counted is in Krebs's description of the method. A Shodan query for MongoDB normally returns a list of database names, many of them defaults like "local". Gevers ran it and saw "far too many" named "readme," "readnow," "encrypted" and "readplease", each holding one document with a contact address and a demand. Merrigan's check: wait a few minutes, re-run the query, and the same addresses "now have a different database title and a new ransom note". So the count was of ransom-note names seen through a scanner, with each host counted under whichever note was written last. The denominator moved too: 99,000 from Gevers, more than 52,000 from Shodan, about 42,000 implied by Bleeping's "25%".

The document behind every January figure is a Google sheet. Its first tab has one row per actor, 109 rows in all, with the name of the replaced database, the ransom, the bitcoin transactions seen, a "Victims (OSINT)" column and a "Victims (helped)" column. The totals row, undated and cumulative to 2019, reads 283 transactions, about 26.9 bitcoin received, 86,993 victims found by open-source means, 102 helped. Merrigan kept it, Krebs says, "on his personal time". That is the instrument. It is a good one for what it measured, which was notes, not data.

The wave came back. Bleeping, 4 September 2017: three new groups had "hijacked over 26,000 servers" in a week, 22,449 of them by one group, taking the tracked total to "over 45,000". Gevers's open questions that day are the chapter's: "Is this a lack of knowledge? Did they mess up the [MongoDB] security settings without knowing it? Are they running on older version without safe defaults and other vulnerabilities?" Four days later the vendor's Davi Ottenheimer wrote that the new wave "does not indicate a new risk, just new targets".

The mechanism

OWASP defines the category as Security misconfiguration is when a system, application, or cloud service is set up incorrectly from a security perspective, creating vulnerabilities. Two lines from its list of symptoms are this chapter: Unnecessary features are enabled or installed (e.g., unnecessary ports, services, pages, accounts, testing frameworks, or privileges). and For upgraded systems, the latest security features are disabled or not configured securely. The page notes that its Notable CWEs included are CWE-16 Configuration, the widest entry on the whole list. Nothing in this chapter is a bug. Every line of code did what it said.

The whiteboard has two switches. A server process listens on an address and a port. Bound to 0.0.0.0 it answers on every interface the machine has, including the public one; bound to 127.0.0.1 it answers only to programs on the same machine. MongoDB's port is 27017. The second switch is authentication, which asks a connecting client who it is. With the first switch open and the second off, whoever finds the port has the database. The attack in the record is only that: Merrigan's summary, via Krebs, was "Use Shodan to scan for open MongoDB databases, connect using anonymous access, and then list all available databases."

Now the first switch, from the record, which shows three defaults. The first was the binary's. Before April 2017 the server's listener read, for an empty bind setting:

if (*ips == '\0') {
    out.push_back(SockAddr("0.0.0.0", port));  // IPv4 all

and the option's help text said "comma separated list of ip addresses to listen on - all local ips by default". Nothing set meant everywhere. The second default was the package's. In November 2011 Roman Shtylman filed SERVER-4216 against the Debian package: its mongodb.conf "Does not have a 'bind_ip 127.0.0.1' option set". His ask: "The default should be to lockdown as much as possible and only expose if the user requests it". It was closed on 8 April 2014 with fix version 2.6.0-rc0, the day 2.6 shipped. From then the RPM and DEB packages wrote a config line that said localhost; the binary underneath still said everywhere. The 3.6 release notes put it exactly: "From MongoDB versions 2.6 to 3.4, only the binaries from the official MongoDB RPM … and DEB … packages would bind to localhost by default."

The third default is 3.6's, and it is the same line of code with a different constant: SockAddr("127.0.0.1", port); // IPv4 localhost. That is the whole change. Who had none of the three? Anyone on a tarball, anyone on a version older than 2.6, and anyone on an image built from either. Matherly's 2015 census: 2.4.14 "seems to be the last version that still listened to 0.0.0.0 by default", and 40 per cent of exposed instances were on 1.8.1. The exposed hosts sat in clouds, where "cloud images don't get updated as often".

And there is a fourth population, which the folk story leaves out. In December 2015 the single most common exposed version was 3.0.7, a version whose packages already defaulted to localhost. Matherly's reading: "a lot of people are changing the default configuration of MongoDB to something less secure and aren't enabling any firewall"; possibly "upgrading their instances but using their existing, insecure configuration files". That is OWASP's "upgraded systems" line, observed thirteen months before the wave. A default that lives in a package's config file is a property of one install path, not of the product. Every other path inherits the binary's answer, and a config file copied from a 2013 tutorial carries its own.

Why it is hard to see: the safe setting looks like a broken one. A database bound to localhost refuses the application server next to it, and the shortest fix on any forum is the one the vendor itself prints in the fix ticket's summary: bindIp: 0.0.0.0. The second switch was never moved. Eliot Horowitz, MongoDB's CTO, on 3.6: "If you explicitly turn it on, but don't turn on authentication, we can't help you at that point." Authentication is off by default in 3.6 as it was in 1.8. The new default does not close the door; it moves the door one step further from the tutorial.

The defense

Read the vendor's statement next to the change it shipped. On 6 January 2017 the advice was: the RPM installer already binds to localhost, "Use this configuration too if you're installing via another means". On 7 March, nine weeks later, Spencer Jackson of MongoDB filed SERVER-28229, "Bind to localhost by default": "MongoDB binaries should bind to localhost by default. This will allow small deployments and testing environments to be used from localhost, while not being accessible from the internet". The spec had three parts. Bind to 127.0.0.1 (and ::1 with IPv6) unless told otherwise. Print a startup warning when no bind address was given. Add a --bind_ip_all flag for those who want the old behaviour. Jackson's commit was authored on 25 April and merged on 28 April 2017, touching 31 files, fix version 3.5.7.

The warning the commit added is the best single line in the defense record, because it names the trade-off:

** ATTENTION: The server is bound to localhost.
**          Remote systems will be unable to connect to this server.
**          Start the server with --bind_ip <address> to specify which IP addresses it
**          should serve responses from, or with --bind_ip_all to bind to all interfaces.

Downstream saw it at once: the official Docker image's maintainers opened an issue that "3.5.7 now binds to localhost-only by default" and that the new flag "does pose complications" for their setup. On 17 May the ticket's user summary said "as of this release, MongoDB servers will only listen for connections on the local host unless explicitly configured to listen on another address". Ottenheimer's September post laid out all three defaults in the vendor's own words. Localhost binding "since release 2.6.0 … in our most popular deployment package formats, RPM and deb". Then: "Beginning with development release version 3.5.7, localhost-only binding is implemented directly in the MongoDB server". And "a warning to our download center" for "non-packaged distributions".

General availability came on 8 November 2017. The London press release: "The most popular installer for MongoDB already limits network access by binding to localhost by default. With MongoDB 3.6, this default behavior is implemented directly in the server itself, so all MongoDB packages across all platforms refuse all external connections to the database unless otherwise explicitly configured by the administrator". The manual today lists net.bindIp with "Default: localhost", and its security checklist's first network item is "Limit Network Exposure". The sequence is the real post-mortem. The statement in January said users must set it; the ticket in March said the product would; the release in November said it did. Seven months passed between merge and GA, and the September wave fell inside them.

Did it work? Take the measurement with its method. Matherly's 2015 census pulled every MongoDB banner from Shodan, shodan download --limit -1 mongodb "product:MongoDB", and summed the reported database sizes. It found "nearly 30,000 instances" without authorization and 595.2 TB in July 2015; "at least 35,000" and 684.8 TB in December. January 2017's "more than 52,000" survives only as Krebs quoted it; Shodan published no post that month. Then, in May 2020, Matherly's after-figure: exposed MongoDB data fell "from 24 TB to 12.5 TB" between 2018 and 2020, "the only database among the 3 I looked at where the amount of exposed data has actually decreased". He also wrote that the 2018 level "was already drastically lower than the others due to a series of ransomware attacks", and that "Those attacks are still on-going".

So the exposed-data series holds, with two caveats the record itself supplies. The 2020 post does not say whether it measured the way 2015 did, so this chapter does not join 684.8 TB to 24 TB as one line. And Shodan's own reading credits the wipes: data fell partly because attackers deleted it. The host count is another matter.

The only after-series is ZDNet's, in July 2020: "From the 60,000 MongoDB servers left exposed online in early 2017, the needle has barely moved to 48,000". It names no source. Its other figure, 22,900 databases ransomed in one 2020 campaign as "roughly 47% of all MongoDB databases accessible online", implies about 48,700 and is consistent only with itself. Shadowserver has scanned for open MongoDB daily for years, tagging hosts with no authentication as "mongodb-noauth" and listing "the first five databases that were returned"; its feed would settle the question and was not obtained for this book. Exposed data fell. Whether exposed hosts fell is contested, and this chapter does not claim it.

What the record does show is the reach of a default. The September 2017 wave, 26,000 in a week, came four months after 3.5.7 and two months before 3.6. In February 2019 another 3,000 were ransomed, and in 2020 the 22,900; ZDNet's explanation was "incorrect MongoDB configuration tutorials", honest mistakes, and "server images that come packed with a misconfigured MongoDB system out of the box". A changed default reaches new installs as they are created and old ones as they are rebuilt, and nothing in between. Horowitz's "that entire method of doing ransomware goes away" is true of the install that keeps the default and of no other.

The defense that reached the installed base was the instrument. The same query that found the victims is the one a defender runs first: Shodan by port 27017 or product name, or Shadowserver's report for your own address space. Nilsson's January post pointed at a Cloud Manager alert "to detect if their deployment is internet exposed"; Ottenheimer's September post at "daily security tests to send alerts on whether their instance is exposed to the public Internet". Here the record is thin: no published figure says how many operators enabled either, and the vendor has published no count of installs that kept the 3.6 default. The measured defense in this chapter is a default, and a default is measured by what it reached.

What you can now see

Take one datastore you run, not only MongoDB, and find out what address it is listening on. Ask the running process, not the config file: the config says what someone meant, the socket says what is true. Then ask where that answer came from. There are only three places it can have come from: the binary's built-in default, a config line the package wrote, or a line a person typed, usually from a tutorial.

If the answer is "every interface" and you cannot name the person and the reason, you have found the finding, before the firewall and before authentication. The 2017 record is exactly that line, written three ways: absent from an old tarball, overridden on a 3.0 host that had shipped safe, and baked into a cloud image nobody rebuilt. Then check the second switch. The 3.6 default moved one; the other is still where it was.
