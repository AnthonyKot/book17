# One Line Too Many, One Field Too Few

Two bugs, ten years apart, that failed in opposite directions.

February 2014. In the code Apple used to secure every connection from its devices, one line appears twice: goto fail. The second copy, wrongly indented, always runs. It jumps past the one call that checks a server's signature, carrying the "no error" left by the previous step. The function returns success from a label named fail. Anyone able to sit on a connection could impersonate any website. No error was ever raised.

July 2024. CrowdStrike pushes a content update to its Windows security sensor. The rule format defined 21 fields. The code had supplied 20 since February. Every test used a wildcard in field 21, so nothing ever looked. One July rule looked. The sensor read past the end of its array, inside the kernel, and Windows stopped 8.5 million machines. The crash text, in Windows' own words: "This cannot be protected by try-except."

Apple's boundary was open where it had to be closed: authentication. CrowdStrike's was closed at the size of a whole machine when the failing unit was one rule. Both fixes were tiny. Neither fix is the lesson.

Check, this week:

Find one place where an error path and a success path share an exit: a cleanup label, a finally, a catch that returns a status variable. If control arrives there with no check having run, what does it return? If "whatever the variable held," and it starts at success, you have Apple's bug waiting for its line.

Then find a component driven by configuration it did not write, and ask what happens the first time that configuration names a field the code never supplied. Decide now how much should crash: the rule, the process, or the machine.
