The Backup That Outlived the Fix

Adobe, 2013. The story says the passwords were never properly protected. The regulators say the proper system had been running for three years. What the attackers took was the copy nobody had deleted.

On 17 September 2013, somebody inside Adobe's network notices an attacker trying to decrypt credit-card numbers in a customer order database. That is how the company finds out. The attacker has been in since 30 August, entering through a public-facing web server and moving from it to other servers. Sixteen days later, on 3 October, Adobe's chief security officer writes that attackers had "accessed Adobe customer IDs and encrypted passwords on our systems".

The passwords are what the world remembers. The database that leaked, and soon circulated freely, held about 150 million accounts. Because of how it had been stored, anyone who read it could see which users shared a password, and a column of plain-text "password hints" sat beside the scrambled values. Security researchers treated the dump as a crossword: the hints were the clues, and the grid told you which clues had the same answer. Within weeks the hundred most common passwords had been worked out, along with the accounts that used them.

The story everyone tells

If you have heard of this breach, you have heard some version of this. Have I Been Pwned, the site people use to check whether their email has leaked, describes 153 million accounts, "each containing an internal ID, username, email, encrypted password and a password hint in plain text", and adds: "The password cryptography was poorly done and many were quickly resolved back to plain text". Wikipedia, citing a password-manager company, says Adobe "failed to use best practices for securing the passwords and has not salted them".

Every sentence there describes the data that leaked. None describes the system that was supposed to have replaced it. That system is in the record, and it changes what the lesson is.

What the regulators found

Three privacy regulators investigated, in Ireland, Canada and Australia, and published reports. Adobe's European operation is in Ireland, and the Irish investigators asked the obvious question: why were passwords stored "in an encrypted manner rather that hashed and salted"? The answer they recorded is the hinge of the story. Adobe "was actually hashing and salting passwords within a new system for a number of years prior to the discovery of the security breach". It had "decided to also keep the database in the old system as a backup measure in case of issues with the new system".

The Australian report dates it. Adobe "introduced a new system in April 2010 as a more secure means of authenticating users than the encrypted passwords stored in the backup system". Adobe told the Commissioner that for more than a year its authentication system had "cryptographically hashed customer passwords using the SHA-256 algorithm, including salting the passwords and iterating the hash more than 1,000 times". Those are the words a security engineer wants to hear: hashed, salted, iterated.

And then, from the same report: "The attacker took a copy of a backup database containing the personal information of customers." The Irish report says the same: "Attackers identified and removed data from a backup server that stored the compromised data." The fix had shipped in 2010. The data it replaced was still on a server in 2013, and it was the data the attackers copied.

The backup was not stale. The Australian count is precise: 1,787,100 Australian users "whose current password data was involved", where current means "a password that was valid against Adobe's production authentication system". Another 218,750 had obsolete password data in the same database. For most of the people counted, the password sitting in reversible form on the backup still opened their account.

Why the dump was a crossword

Two words carry the technical finding, and both are worth understanding even if you never write code, because the same mistake appears in systems you use.

The first is encryption. A password store has one job: to let a server check your password without being able to produce it. Encryption cannot do that job, because encryption is reversible by design. Whoever holds the key can read every password, and the server has to hold the key to check anything. The right tool is a hash, a one-way function. The server stores the hash of your password, computes the hash again when you log in, and compares. Nobody, the server included, can walk back from the stored value to the password except by guessing.

Adobe's old system encrypted, with an algorithm called Triple DES. The second word is the mode it used. Triple DES works on fixed-size blocks of input, and in the mode Adobe chose, every block is scrambled independently under the same key. So the same input always produces the same output. The Australian report says exactly this without the jargon: "common passwords shared by different users had the same ciphertext representation."

Draw the table and the problem is visible without any cryptography:

user        stored value (encrypted)    hint (plain text)
alice@…     2fca9b003de39278            "my dog"
bob@…       2fca9b003de39278            "the usual"
carol@…     2fca9b003de39278            "rex plus year"
dave@…      e2a311d0ff1c5a17            (none)

That is the shape, not real data. Three people with the same password have the same stored value. Anyone reading the table can group users by that value without knowing the key, then read every hint in the group. One careless hint anywhere in the group gives away the password for all of them. The Canadian report describes it in a sentence: "the plain text hints sometimes contained the password itself (or a very obvious hint)", and "the encryption format used by Adobe scrambled identical passwords in the same way", so it "would be relatively easy to obtain access to several different accounts where the same password was used".

Note what this did not need. No report says the encryption key was recovered. The crossword was solved with the clues, not the cipher. And the hints were not universal: the Irish report puts them at "a small percentage of users". A small percentage of 150 million is enough.

The fix, and why it was already built

The proper store differs in two ways. A salt is a random value stored per user and mixed into the hash, so that equal passwords no longer produce equal stored values. The US standards body puts the purpose in one clause: "to prevent multiple subscriber accounts from having the same hashed password". A work factor makes each guess slow, "to make each password guess more expensive for an attacker who has obtained a hashed password file".

Adobe's 2010 system had both properties in its description. The OWASP Top 10, the list of the ten most common classes of web-application weakness that this case belongs to under "Cryptographic Failures", gives the same instruction in one line: "Store passwords using strong adaptive and salted hashing functions with a work factor (delay factor), such as Argon2, yescrypt, scrypt or PBKDF2-HMAC-SHA-512."

So the engineering was not the failure. Something more ordinary was. Encryption feels like protection, and for data you must read back, such as card numbers, it is. A team that has encrypted one table encrypts the next with the same library, and a store that decrypts correctly passes every test a store can pass. The hints were a product feature. And once the new system worked, the old database was kept "in case of issues". The Canadian investigators' list of concerns reads like a description of that decision: "password management, outdated software, redundant systems containing personal information ... retention of data for longer than necessary". Some of those systems, they noted, "had been inherited as a result of absorbing other companies".

The sentence written for this case

The Australian Commissioner found that Adobe "breached NPP 4 by failing to take reasonable steps to protect all of the personal information it held", and then wrote a sentence that applies far beyond Adobe. The obligation "will not be satisfied if an organisation has adequate security measures in place to protect personal information stored in one area of its systems" but "does not implement these measures in relation to all of the personal information that it holds".

That is the rule. Security in one place does not count if the same data sits unprotected in another. A migration is finished when the old store is gone, not when the new one works. The Irish finding says it in a regulator's register: the transition "could have been achieved more effectively and expeditiously than was the case". OWASP says it in plainer words: "Don't store sensitive data unnecessarily. Discard it as soon as possible."

What Adobe did afterward is on the record. Australia lists "decommissioning the affected server and abolishing the use of password hints". Canada lists "a reduction in the retention period for customers' payment data" and enhancements it could not describe because they were commercially sensitive. The hint feature is now forbidden outright by the US standard: a verifier "SHALL NOT permit the subscriber to store a hint ... that is accessible to an unauthenticated claimant". What no report contains is a check that no other copy of the reversible database existed. That question stays open.

The mirror: LinkedIn

A year earlier, LinkedIn had fallen a different way. On 6 June 2012 it "became aware" of "the theft of approximately 6.5 million passwords". Those were not encrypted; they were hashed. But a later paper identifies them as "unsalted SHA-1 password hashes", and adds that LinkedIn "was not using key-stretching tools such as PBKDF2 or Argon2 at the time of the breach", so "the passwords were significantly easier to crack". LinkedIn's own statement of 12 June said it had "completed a long-planned transition" to a system "that both hashes and salts the passwords". Four years later the same 2012 data resurfaced, now at "over 177.5 million" records.

Set the two side by side. Adobe stored passwords reversibly, in a mode that leaked equality, beside plain-text hints, in a backup that should not have existed. LinkedIn stored them irreversibly but fast and unsalted, so equal passwords still matched and every guess was cheap. Neither company lacked the knowledge. Adobe had built the right system and LinkedIn had planned the right transition. Both were caught holding the old store.

The ledger

The book this comes from keeps a ledger for each case: the claim as it circulates, the document that checks it, and a verdict. Here is Adobe's.

  • "Adobe had not salted the passwords." The Irish report records a hashing-and-salting system running for years before the breach; the Australian report dates it to April 2010. The claim describes the leaked backup and omits the production system. Missing the main fact.
  • "Each breached account contained a password hint in plain text." The Irish report: hints belonged to "a small percentage of users". Overstated.
  • "Many passwords were quickly resolved back to plain text." True, but by the crossword of hints and repeated passwords, not by breaking the encryption. No report says the key was recovered. Missing the mechanism.
  • "The breach happened in October 2013." Access ran from 30 August to 17 September; October is the announcement. Overstated.
  • "Every affected customer was forced to change their password." Adobe reset passwords only for users whose current password data was in the database; 218,750 Australians had obsolete data. Overstated.
  • LinkedIn's passwords were "encrypted" and "decrypted" (WIRED, 2012). They were hashed, and hashes are guessed, not decrypted. Wrong.

What you can now check

Find one migration in a system you run, or depend on, that everyone calls finished. A password store moved to a proper hash. A secrets system replaced. A card-number table tokenised. Then ask one question of it: where is the old copy? Not the old code. The old data. A backup taken before the cut-over, a replica never torn down, a nightly export that still runs, a dump on a share "in case of issues with the new system".

If you can name the copy and the date it was destroyed, the migration is finished. If you can only name the new system, you have Adobe's finding: more than three years after the replacement arrived, a retained database still held current passwords in reversible form, and that database is what was taken. Then look for the hint column, or its modern equivalent: any field stored in the clear that helps a reader guess the protected one. The clue beside the ciphertext, not the cipher, is what turned a dump into a crossword.
