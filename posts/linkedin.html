The Firewall Could Read the Bank

In 2019 an intruder took data on about a hundred million Capital One customers.

The story that spread within days: a web firewall was tricked into fetching cloud credentials, a trick called server-side request forgery. The FBI's sworn complaint never uses those words. It says something plainer, and more useful.

The firewall's cloud identity "does not, in the ordinary course of business, invoke the List Buckets Command." Yet one call with that identity returned the names of more than 700 storage buckets. A second call copied from every bucket it had permission to read.

So the bug that mattered was not the forwarding rule. It was a permission. A firewall's job is to inspect traffic and pass or drop it. Nothing in that job requires listing every bucket in a bank. Whatever route the requests took, that policy is what turned a proxy into a bank.

A permitted call by a permitted identity is the hardest thing in a log to see. Nothing fails.

Monday check, no attacker needed:

Pick one machine you run that forwards requests: a firewall, a proxy, a gateway. Find the identity attached to it. Open the policy, not the wiki. Beside each permission, write the machine's job in five words. Any line with no job beside it is the finding. Look at list permissions first: a stolen key that can list is a map of the account.

The complaint, twelve pages, allegations not findings: https://www.justice.gov/usao-wdwa/press-release/file/1188626/download

The Backup That Outlived the Fix

October 2013. Adobe announces that attackers took customer IDs and encrypted passwords. The database that leaks holds about 150 million accounts, and next to each scrambled password sits a plain-text "password hint."

The story everyone tells: Adobe never protected passwords properly. No salt, weak cryptography, quickly cracked.

Three privacy regulators investigated. What they found is stranger. Adobe had built the proper system, hashed, salted and iterated, in April 2010. It had been running for three years. The company kept the old encrypted database "as a backup measure in case of issues with the new system."

The attackers took the backup.

And the backup was not stale. In Australia alone, 1.8 million users had a password in that old copy that still opened their account. Nobody broke the encryption. The dump was a crossword: identical passwords scrambled identically, so anyone could group users by stored value, then read every hint in the group. One careless hint gave away the password for all of them.

The Australian Commissioner wrote the sentence this case exists for. Security "will not be satisfied if an organisation has adequate security measures in place to protect personal information stored in one area of its systems" but not in all of them.

A migration is finished when the old store is gone, not when the new one works.

Check, this week:

Find one migration everyone calls finished. A password store, a secrets system, a card table. Ask one question: where is the old copy? Not the old code. The old data. A backup from before the cut-over, a replica never torn down, an export that still runs. If you can name it and the date it was destroyed, the migration is finished. If you can only name the new system, you have Adobe.

The Australian investigation report: https://www.oaic.gov.au/privacy/privacy-assessments-and-decisions/privacy-decisions/Investigation-inquiry-reports/adobe-systems-software-ireland-ltd-own-motion-investigation-report

What "Turn Off GPS" Left Out

January 2018. A student in Australia opens Strava's global heatmap, two years of runs and rides from millions of users, and looks at Syria. Most of the country is dark. A few neat rectangles glow in the desert. They are the running routes on military bases.

The headlines: Strava gave away secret bases. The Pentagon banned fitness trackers.

The record: the map worked exactly as designed. Every activity on it was one its user had made public. The design was the problem.

In a city, one run disappears into thousands. In a desert, five people's daily run is the only thing on the map, and it draws the fence line. Strava's own engineer wrote that the colouring was relative, so quiet places got maximum contrast, and that the map "is not absolutely quantitative." No scanner finds that. The code had no bug.

Strava's fix was not a patch. It was a threshold: no heat until several different athletes had passed. And the Pentagon did not ban anything. Its memo restricts geolocation in designated operational areas and allows exceptions after a security survey the department already required, and had not been running.

Check, this week:

Find one aggregate you publish: a heatmap, a leaderboard, a "popular near you." Assume every row was shared on purpose. Ask what a hostile reader learns where the aggregate is nearly empty. If it has no minimum below which it shows nothing, you have Strava's design.

The memo, three pages: https://media.defense.gov/2018/Aug/06/2001951064/-1/-1/1/GEOLOCATION-DEVICES-APPLICATIONS-SERVICES.PDF

The Door Colonial Could Not See

May 2021. A ransomware note appears on an office computer at Colonial Pipeline before five in the morning. By ten past six, all 5,500 miles of fuel pipeline are shut down. Most of the US East Coast spends a week short of petrol.

The story that settled within a month: one leaked password, a VPN account with no second factor. True, and the least useful version.

A month later the chief executive testified to the Senate. Colonial's normal remote access did use a second factor, a hardware token. One legacy VPN profile sat outside it. It was "not intended to be in use." It was believed disabled. And it accepted a username and a password on 29 April.

His sentence, under oath: "That we could not see and it did not show up in any pen testing, that is unfortunate."

Belief about a configuration is not a configuration. A door you think is bricked up, that still opens for a key, is the door an attacker uses. The password mattered. The record's subject is the door.

Check, this week, no attacker needed:

Draw your perimeter as a table, not a wall. One row per way in: each VPN profile, remote-desktop gateway, service account, vendor portal. One column: what that row demands, password only, password plus code, password plus key. The perimeter is not the average of the column. It is the weakest row. Then test the rows documented as disabled, by trying to log in.

The Senate hearing, full transcript: https://www.govinfo.gov/content/pkg/CHRG-117shrg46569/html/CHRG-117shrg46569.htm

The Backup That Was Not a Backup

27 June 2017. Screens at Maersk, the company that moves a fifth of the world's container trade, go black and show a ransom note. Within hours: no email, no bookings, no way to tell a port which box goes on which ship. Ten days to rebuild. 250 to 300 million dollars.

The story everyone tells ends in Ghana. Maersk's identity system ran on about 150 servers worldwide, constantly synchronising. The malware wiped them all, except one in Ghana that a power cut had knocked offline. Its disk was flown to London and the company was rebuilt from it.

It is a good scene. Maersk's own identity engineer, Gavin Ashton, draws the lesson differently. The recovery plan covered losing a site. It had not covered losing every controller everywhere at once. Even the magazine that made the scene famous concedes the synchronised servers "had not accounted for every controller being wiped simultaneously."

That is the whole lesson. A live replica answers one question: can another machine serve the latest state? A backup answers a different one: can we recover a known earlier state after the latest state has become dangerous? Ghana was the second thing, by accident.

Check, this week:

Find the copy of your critical state that survives if destructive code can reach every current peer through the same administrative paths. If the answer is another live replica, you have availability. You have not yet drawn recovery.

Ashton's account, written as a participant: https://gvnshtn.com/p/maersk-me-and-notpetya

One Line Too Many, One Field Too Few

Two bugs, ten years apart, that failed in opposite directions.

February 2014. In the code Apple used to secure every connection from its devices, one line appears twice: goto fail. The second copy, wrongly indented, always runs. It jumps past the one call that checks a server's signature, carrying the "no error" left by the previous step. The function returns success from a label named fail. Anyone able to sit on a connection could impersonate any website. No error was ever raised.

July 2024. CrowdStrike pushes a content update to its Windows security sensor. The rule format defined 21 fields. The code had supplied 20 since February. Every test used a wildcard in field 21, so nothing ever looked. One July rule looked. The sensor read past the end of its array, inside the kernel, and Windows stopped 8.5 million machines. The crash text, in Windows' own words: "This cannot be protected by try-except."

Apple's boundary was open where it had to be closed: authentication. CrowdStrike's was closed at the size of a whole machine when the failing unit was one rule. Both fixes were tiny. Neither fix is the lesson.

Check, this week:

Find one place where an error path and a success path share an exit: a cleanup label, a finally, a catch that returns a status variable. If control arrives there with no check having run, what does it return? If "whatever the variable held," and it starts at success, you have Apple's bug waiting for its line.

Then find a component driven by configuration it did not write, and ask what happens the first time that configuration names a field the code never supplied. Decide now how much should crash: the rule, the process, or the machine.

CrowdStrike's root-cause analysis, twelve pages: https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf
